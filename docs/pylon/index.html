Pylon: an AWS runtime for internal AI agents

I built Pylon to answer Swisscom's AI Platform Engineer job post, one point at a time. It is built to run an AI agent on Fargate behind Entra sign-in, write an audit record for every query and alarm on its SLOs. A per-user token quota guards spend, and a budget alarm scales the agent to zero if spend runs past the cap.

The code and its tests pass offline. No row has live evidence yet: live tests are in progress. Each row below has a badge that says which state it's in.

Watch the 3-minute demo Read the evidence

What you can adopt on day one

  • Nine Terraform modules (network, KMS, edge, agent service, tools, audit, observability, chaos, FinOps), composed into dev, staging and prod roots, each with its own state.
  • A front door with no load balancer and no NAT gateway: CloudFront and WAF, an HTTP API that checks the Entra token, then a VPC Link to the agent on Fargate.
  • A model gateway to Bedrock with a second model as fallback, and a canned answer when both fail.
  • One audit record per query in an S3 Object Lock bucket, queryable in Athena.
  • Six alarms on five SLIs, with the error-budget math written out in the SLO document.
  • A per-user daily token quota, a daily cost report by team, and a budget kill switch that scales the agent to zero.
  • Five runbooks and a STRIDE threat model over five trust boundaries.

What you must adapt

  • Identity: point the JWT authorizer at your Entra tenant, audience and roles claim. Mine is a free test tenant.
  • Network: dev runs in one availability zone on public subnets. The prod setting (private subnets, two zones, VPC endpoints) exists in code and has never been applied.
  • Deploys: my AWS Organization blocks GitHub OIDC, so I deploy from my terminal (D-44). The OIDC roles are written and tested behind one flag. Turn it on if your organization allows it.
  • Region and models: I picked eu-north-1 because of Bedrock availability (D-19). Check which models your account can call.
  • SLO targets: these are my starting values for a dev demo, not contracted levels.
  • Standards: I don't know Swisscom's security, compliance or network rules. Every guess I made is in the assumptions file.

What this project cannot show

These are the limits of a solo project that matter for this role.

  • Kubernetes. I chose ECS Fargate over EKS on cost (D-04). Pylon has no Kubernetes in it.
  • High availability. Dev runs in a single availability zone by design (D-14). The two-zone prod setting is code only.
  • On-call history. Pylon is a showcase deployment, and no row has live evidence yet, so there is no on-call record to show.
  • Pairing with security teams. A solo project cannot show it. The STRIDE threat model is the closest artefact.
  • Swisscom's own standards. I don't know them. Every Swisscom-specific guess is in the assumptions file.
  • Live evidence. Nothing is verified in AWS yet. Live tests are in progress, and a badge changes only when its evidence is linked.
